# コミュニティベンチマーク: Intel Arc Pro B70 4 枚（SYCL、層の分割）

[English](README.md) | 日本語

2026-10-12 に JP-devv が測定。**上流のソースそのまま**、commit `8607e667`（xe0.1.43.1）、ツリーは
クリーンで**エンジンへのローカルな変更は無い**。リリースとの差は以下の実行設定だけである。Unsloth の
**UD-Q4_K_XL**、文脈 131,072、層の分割は 4 枚すべて、MTP の下書き層あり。見出しの数字は 3 回の
中央値（プロンプト 4,154 / 32,702 / 127,531 トークン）で、**PP 1,111 / 1,869 / 2,233 トークン/秒**、
**TG 78.5 / 72.0 / 72.5 トークン/秒**。

`docs/MULTIGPU.md` は同じファイルを B70 1 枚で 20.8 トークン/秒、B70 + RTX 4070 で 38.3〜39.0 と
測っており、これは 1 枚の約 3.5 倍にあたる。主な限界: 1 台で 1 モデル、品質の確認は下書きの採択と
CTest まで（それ以外は無し）、長さごとにプロンプトの形は 1 種類（「制限」を参照）。

## ハードウェアとソフトウェア

- GPU: **Intel Arc Pro B70 4 枚**（Xe2）、1 枚あたり 31.9 GiB 使用可、4 枚すべて使用、1 枚あたり
  275 W の上限（hwmon `power1_cap`）。4 枚は 1 つのルートコンプレックスの PCIe スイッチの枝の先にある。
  カードやその上流ポートでリンクを読むと `x1 2.5GT/s` になるが、これは内部のポートであって
  データの通り道ではない。エンジン自身の自動分割の探査は 64 KiB のホスト→デバイスのコピーで
  **26.7 GB/s**、[p2p-bw.cpp](p2p-bw.cpp) はホストのメモリーを経由して端から端まで **12.6 GB/s**
  （2 区間なので 1 区間あたり約 25 GB/s）。[system.json](system.json)、
  [environment.json](environment.json) を参照。
- CPU: Intel Core i7-13700K（24 スレッド、AVX2、**AVX-512 なし**。したがって AVX-2 のエキスパート
  カーネルが走った）。RAM: 64 GB DDR5（OS から見えるのは 61 GiB）。モデル・pack・MTP の素は
  1 つの NVMe パーティションにある。
- OS: Ubuntu 26.04.1、kernel 7.2.10、`xe` ドライバー、Level Zero `libze-intel-gpu1` 26.18.38308.1。
- コンパイラ: **intel/llvm v7.1.1**（`504366f4`）を `tools/intel_llvm_build.py` でソースから構築、
  libsycl 9。oneMKL 2026.1。oneAPI 2026.1.1 は入っているが未使用（それは contrib-icpx モードで、
  この記録の対象ではない）。
- 裏で動くもの: 同じ 4 枚の GPU を使う無関係なサービスはすべての測定で止めた。エンジンのログには
  このベンチマークの要求（同時に 1 つ）しか出ていない。

## ビルド

`free` と `contrib-llvm` の**両方**で `STRATA_BUILD_TESTS=ON` としてビルドと試験を行い、**どちらも
CTest 92 件が 92 件とも通った**。測定に使ったのは contrib-llvm のバイナリである（プロンプト経路の
密な行列積は oneMKL、それ以外は XeStrata 自身の XMX カーネル）。free のバイナリはビルドと試験までで、
測定はしていない。`contrib-icpx` はビルドしていない。[build.json](build.json) にコンパイラの記録、
[BUILD.md](BUILD.md) に伝えておく価値のあるビルド環境の注意が 1 つある。

## モデルと設定

- モデル: [`unsloth/Qwen3.8-Flash-Next-GGUF`](https://huggingface.co/unsloth/Qwen3.8-Flash-Next-GGUF)
  の `UD-Q4_K_XL`、リビジョン `38bb39ee97821de2c9009abb7e93950eec396e66`。4 シャードとも `setup.py`
  が固定する表の SHA-256 と一致（合計 111,334,654,784 バイト。各ファイルは `10,946,624`、
  `49,859,583,136`、`49,376,141,504`、`12,087,983,520` バイト）。
- pack: `iq_pack.py --compat-bf16`（Q8_0 のハイパー接続の射影を、エンジンが読む BF16 に変える）。
  エキスパートは GGUF に残り、その場で読まれるので、アリーナ全体の RAM 写しは取られない。n-gram の
  表は SSD から読む（`--ple-io direct`。エンジンの探査は 139,373 行/秒と報告した）。
- MTP: `tools/mtp_fetch.py` で BF16 のチェックポイントから構築（`mtp.*` の 31 テンソル @
  `Qwen/Qwen3.8-Flash-Next@de4b8e4d43b917e7706784d8bb445c9af86a3540`、各テンソルを固定リビジョンの
  SHA-256 と照合し、`verify` は 0 で終わる）。q2_0 に pack し、実行用の素に組み立てた。
- 設定: [configurations.json](configurations.json)。`setup.sh` が書くものに加えて:
  **`--layer-split 5,24,43`**（固定。以下を参照）、`--pipeline-windows 2`、
  `--expert-cache-per-layer`、`--pcie-frac 0`、`--adapt-every 0`、`--spec 3`、
  `--resident-budget-gib 8`（setup の 35 から下げた）、`--kv-resident` を**削除**（0 = KV をすべて
  VRAM に。131072 の int8 で 4 枚合わせて約 1.8 GB）、そしてエンジンの環境に
  `STRATA_SPLIT_CPU_GBPS=5` と `STRATA_SPLIT_MTP_BATCH=0`。
- 決まった配置: 層 0–4 / 5–23 / 24–42 / 43–47。トークングラフで**21,952 のエキスパートが常駐**し、
  段ごとのキャッシュは 2,560 / 2,560、9,565 / 9,728、9,529 / 9,728、2,560 / 2,560 対
  （[engine-startup.txt](engine-startup.txt)）。実行中の decode のエキスパートキャッシュ的中率は
  93〜94%（残りは MTP の下書き層自身のエキスパートと、プロンプト経路の流し込みで、層ごとの
  キャッシュはそこを覆わない）。

## 結果

方法: 捨てる warm-up を 1 回、そのあと長さごとに 3 回、温度 0、生成の上限 256 トークン、同時 1 要求。
**PP** は prompt（prefill）のトークン/秒、**TG** は decode のトークン/秒。測った実行はすべて
プロンプト全体の読みで、測定器はプロンプトの先頭を変えて会話キャッシュに拾わせない。これが cold の
場合で、実際の使い方では続きは新しい分しか読まない。

| プロンプト（トークン） | PP トークン/秒 | TG トークン/秒 | 下書きの採択 |
| ---: | ---: | ---: | ---: |
| 4,154 | 1,111.4（1,109.1〜1,111.9） | 78.5（76.3〜79.0） | 177〜183 のうち 132〜138 |
| 32,702 | 1,868.6（1,868.3〜1,868.7） | 72.0（71.9〜84.9） | 176〜177 のうち 128〜143 |
| 127,531 | 2,233.0（2,232.3〜2,233.4） | 72.5（71.7〜73.1） | 169〜191 のうち 129〜137 |

実行ごとの値: [results.csv](results.csv) と [matrix.jsonl](matrix.jsonl)（どちらもエンジン自身の
要求行から起こしたもの。[engine-requests.txt](engine-requests.txt)）。中央値と範囲:
[summary.json](summary.json)。

**再現の確認。** 埋め草のプロンプトの 10%、50%、90% の深さに 5 桁の符号を 1 つ埋め、あとから
問い返す（温度 0、思考 off、1 つのセルにつき新しい文脈で 1 回の要求なので、どのセルも
プロンプト全体の cold な読み）。結果は **9 セル中 9 セルで再現** — 4K（3,630 トークンの
プロンプト）、32K（28,786）、128K（115,016）。セルと応答は [needles.json](needles.json)、
確認そのものは [needles.py](needles.py)。再現の確認は、答えの品質一般については何も言わない。

## 数字が示すこと

**TG は 128K まで平坦**（72〜79。文脈の長さによる目立った低下は無い）。KV キャッシュが VRAM に
あり、48 層のうち attention は 12 層だけだからである。**PP はプロンプトが長いほど上がる**
（1,111 → 2,233 トークン/秒）。バッチのプロンプト経路が、長いプロンプトほど 1 回あたりの起動と
塊ごとの費用を薄められるためで、このエンジンで PP が最も悪いのは短いプロンプトである。PP は
非常に安定している（上の範囲は 0.3% 未満）。TG は回ごとに ±8% 動くので表に範囲を添えた。

**この機械では、自動分割の選択は再起動ごとに変わらない。** 同じ設定で、`--layer-split auto` と
`STRATA_SPLIT_CPU_GBPS=5` は、ある起動では **5 / 19 / 19 / 5**（21,952 対が常駐）を、次の起動では
**4 / 23 / 30**（**24,303** 対、経路の質量の約 99.7%）を選んだ。候補どうしが近く、計画器自身が測った
速度が回ごとに勝者を決めている。したがってこの記録は測定したときの配置を固定し、そのまま書いて
ある。参考として、setup が書く既定の CPU 速度（この機械では 88 GB/s と測られる）では
3 / 30 / 3 / 12 を選ぶ — 18,240 対で、2 枚が約 40 GB の VRAM を使えないまま抱える。

**`STRATA_SPLIT_CPU_GBPS` を下げると選択は良くなり、完全常駐の分割が最も速いわけではない。**
1K で 5 回ずつ:

| 1K、5 回の中央値 | auto + `CPU_GBPS=5` | `--layer-split 12,24,36` を明示 |
| --- | ---: | ---: |
| PP トークン/秒 | **475.1**（475.0〜479.1） | 448.2（437.9〜449.9） |
| TG トークン/秒 | **78.0**（69.6〜80.8） | 72.5（63.9〜78.6） |
| 常駐する対 | 21,952（5/19/19/5） | 24,576（12/12/12/12） |

PP の範囲は重ならない。TG の差は散らばりの中にある。`CPU_GBPS=1` はさらに悪く（10 / 3 / 17、
20,618 対、TG 77.2 / 73.0）、3 段（`--layer-split 16,32`、1 枚は遊ぶ）は明確に悪い（TG 67.2 / 69.4）。
常駐の少ない分割が勝つ理由はおそらく次のとおり: 最初の段が埋め込みの集約・ハイパー接続の配信・
PLE の塊を担い、最後の段が出力ヘッドと MTP の下書き層を担うので、この 2 段は層あたりの費用が
中央の段より高い。**段ごとの時間**を均すほうが層数を均すより良い、というわけである。400 トークン
生成中のカードごとの仕事の割合も同じことを言う（[power-balance.jsonl](power-balance.jsonl)）:
合計 499 W のうち card0 19%、card1 29%、card2 26%、card3 26%。nvtop の使用率が揃わないのは
想定の範囲で、不具合ではない。

**この機械では P2P が使え、エンジンは使っていない。** `zeDeviceCanAccessPeer` は 12 組すべてに
YES を返し、256 MiB のコピーの実測は、デバイス→デバイスが **25.6〜28.7 GB/s**、いまの層の
受け渡しが通るホストのメモリー経由が **12.6〜12.7 GB/s** である（[p2p.json](p2p.json)、
[p2p-bw.cpp](p2p-bw.cpp)、[l0-peer.py](l0-peer.py)）。この構成の助けにはならない（受け渡しは
1 トークンあたり約 50 KB）が、補助の層やエキスパート並列の配置がエキスパートの塊に使う
ファブリックではある。エンジンには peer の経路が無いので、その設計はここでは測っていない。

**setup が書くモデルごとの設定は 1 枚のカードを前提にしている。** VRAM に収まる KV キャッシュを
ホスト RAM へ流し（外すのは無料だった）、既に常駐しているエキスパートのために RAM を確保し
（残りのミスの保険として 8 GB だけ残した）、`--expert-cache-per-layer` はヘルプ自身が害を書いて
いるのに既定では入っておらず、起動時には
`WARNING: RAM is tight - the model's experts take 71.7 GB of this PC's 61 GB` を出す。GPU がモデルを
抱え、RAM へは約 8 GB しか写さない構成では、これは故障のように読める。

## 制限

- 1 台で 1 モデル（UD-Q4_K_XL）、長さごとに繰り返しの英文 1 種類。TG はテキストと下書きの採択で
  数% 動くので、隣り合う値は意味を持たない。
- 品質の確認は、プロジェクトの CTest と、下書きの採択数と、上の再現の確認まで。perplexity も
  課題の点数も測っていない。
- 測っていないもの: 127,531 トークンを超える文脈（262,144 の窓は使っていない）、温度 0.7・serve 経路・
  通常使用の数値、free モードのバイナリの速度（ビルドと試験のみ）、`contrib-icpx`、画像（off）、
  AVX-512 のエキスパート経路（この CPU に無く、Intel SDE も使っていない）、Q2_0 の AVX-512 の
  pack、2 段の分割、`STRATA_SPLIT_ROWS` / `STRATA_SPLIT_MASS_EXP`。
- P2P の数値は 256 MiB のコピーによる。小さいコピーの遅延（受け渡しや 1 つのエキスパートの塊が
  そうである）は測っていない。
