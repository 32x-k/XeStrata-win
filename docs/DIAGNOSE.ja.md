# LLM エージェントへの復旧と原因調査の指示

[English](DIAGNOSE.md) | 日本語

端末を操作できる LLM エージェントに、この文書と「何をしようとして、どう動かなかったか」を渡してください。
git clone などで導入したソース版と、apt/dnf などで導入した deb/rpm 版を対象にしています。
以下はエージェントへの指示です。

## 目標と作業の進め方

この PC で XeStrata が動かない原因を調べ、復旧できるなら復旧してください。
最後に、解決した場合も未解決の場合も、開発者が確認できる根拠を付けて[報告](#報告の形式)してください。
利用者が困っている操作を成功させることを目標にします。
画像や複数 GPU の要求があるなら、その操作まで確認してください。

1. 最初に、失敗した操作、実行対象、版、設定、エラーを保存してください。
   更新や再設定の前に、変更前の状態を辿れるようにします。
1. 利用者の指定と与えられた権限の範囲で、必要な設定修正、依存関係の導入、ダウンロードの再開、ビルドや局所的なコード修正を進めてください。
   変更の理由と変更前後の値を、秘密を含めずに記録してください。
1. 原因候補を一つずつ検証してください。
   複数の変更を同時に適用した場合は、どの変更が効いたか特定できていないことを報告してください。
1. 権限不足や、再起動、既存サービスの停止、データの削除などが必要なら、必要な操作と影響を具体的に示して確認してください。
   無関係なプロセスや利用者のファイルを変更せず、その間に進められる調査を続けてください。
1. 実行の待ち時間と再試行回数には限度を設けてください。
   ログや CPU/GPU/I/O の進み方を見て、時間のかかる初回読み込みと停止を区別します。
   新しい証拠を得られなくなったら、残る仮説と次に必要な確認を報告してください。

API キー、認証情報ストア、環境ファイル、私的な会話をそのまま表示したり、エージェントの入力や共有資料に含めたりしないでください。
設定と環境変数は、必要な項目だけをローカルで抽出してください。
認証は既存のクライアントの正規の認証方法を使い、キーをコマンドの引数や報告に書かないでください。
秘密を含む設定の修正は、その値を表示せず、バイト単位で保持できる場合に限ります。
元ログはローカルに残し、秘密を除いた必要な抜粋を使ってください。
共有する報告では、利用者名、個人のパス、ホスト名、IP アドレスを一貫した仮名に置き換え、ソースの相対パス、行番号、ライブラリ名は残してください。
報告や issue の外部送信は利用者に任せるか、明示的に依頼されたときに行ってください。

## 変更前に残す情報

まず既存のログと利用者の説明を調べ、次を記録してください。
不明な項目は不明と書き、調べられるものを先に調べてください。

| 項目 | 記録する内容 |
| --- | --- |
| 症状 | 期待した動作、実際の動作、最初に失敗した段階、エラー原文と前後のログ |
| 再現条件 | 実行コマンド、作業ディレクトリ、起動方法、入力、発生日時とタイムゾーン、初回か再起動後か |
| 頻度 | 毎回か間欠的か、試した回数、直前に成功した版や条件、その後に変えたもの |
| 実行対象 | ソース版か deb/rpm 版か、起動する実行ファイル、実行バイナリの版、対応するソースの版 |
| モデル | 配布元、取得した版、モデル名、量子化形式、GGUF の全分割ファイルの名前とサイズ、pack と MTP の有無 |
| 要求と設定 | 選んだ GPU、複数 GPU の分割、文脈長、KV、CPU スレッド数、省 RAM の設定、推測デコード、画像、並列数、射影など症状に関係する項目 |

私的な入力が再現に必要な場合は、同じ失敗を起こす共有可能な短い入力に縮めてください。
置き換えると再現しなくなるなら、その事実と、共有できる入力の構造や長さを残してください。
モデル破損を疑うときは、分割数とサイズ、途中の `.part`、取得時の検証記録を確認し、必要なファイルだけ配布元のチェックサムと照合してください。
完了を示すファイルや名前だけでは、内容が正しい証拠になりません。

## 導入方法と実行中の版を特定する

ソース版とパッケージ版が同居していることがあります。
利用者が実行したコマンド、起動スクリプト、設定の `exe`、動いているプロセスの実行ファイルから、実際の対象を特定してください。
手元のソースが新しくても、実行バイナリが同じ版とは限りません。

### ソース版

対象のリポジトリで、コミット、タグ、変更の有無を確認してください。

```bash
git rev-parse HEAD
git describe --tags --always
git status --short
```

エンジンの設定の `exe` を辿り、そのバイナリの `--version` と、隣にある `BUILD.json` を確認してください。
実行には、元の起動方法と同じライブラリの環境を使います。
setup が作ったものは通常 `engine/` にあり、手動の CMake ビルドは別のフォルダーにあることもあります。
ビルドフォルダー名からビルドモードを断定しないでください。

コンパイラの実体と版、CMake の実行条件、`CMakeCache.txt` の関係する項目、依存するプロジェクトの版を記録してください。
主に `STRATA_LICENSE`、`STRATA_CUDA_ARCHS`、`STRATA_HIP_ARCHS`、`STRATA_ONEMKL`、`STRATA_PORTABLE` と、エンジンや画像のビルド条件を確認します。
報告では free、contrib-llvm、contrib-icpx を区別してください。
`STRATA_LICENSE=contrib` は contrib-llvm です。

ソース版は、更新後のビルドに失敗すると以前のエンジンを保持して起動することがあります。
Git のコミット、ビルド情報、実行バイナリの版を別々に記録してください。
setup の `BUILD.json` の `src` はソースの指紋であり、Git のコミット ID ではありません。
変更された関係箇所は、秘密を含まない差分だけを報告に添えてください。

### deb/rpm 版

まず `command -v xestrata` で起動コマンドを特定してください。
deb 版では次のように、実際に入っているパッケージを確認します。

```bash
dpkg-query -W -f '${binary:Package} ${Version} ${Architecture}\n' 'xestrata*'
```

rpm 版では次を使います。

```bash
rpm -qa --qf '%{NAME} %{VERSION}-%{RELEASE} %{ARCH}\n' | rg '^xestrata'
```

`rg` がなければ、同じ絞り込みを使える道具で行ってください。
パッケージのファイル一覧と所有元も確認し、別の導入先のコマンドを実行していないか調べてください。
起動コマンドが参照する XeStrata のフォルダーの `PACKAGED` から、同梱エンジンの場所を辿れます。
その `BUILD.json` と実行バイナリの `--version` を確認し、パッケージの版、ビルドモード、コンパイラ、GPU のターゲットを記録してください。
パッケージの版とタグの対応は [BUILD](BUILD.ja.md#パッケージの中身) にあります。

パッケージ版には SYCL のランタイムが同梱され、GPU のドライバや一部の計算ライブラリは別途入れたものを使います。
Python のパッケージはディストリビューションのものを使います。
症状に関係するパッケージの版と読み込まれるライブラリを調べてください。
XeStrata 自体がソース版であることを前提に再ビルドしないでください。
コードの調査が必要なら、失敗したパッケージの版に対応するタグのソースを別の調査用フォルダーで読み、インストール済みのファイルを保存してください。
一致を確認できないソース位置は参考として扱ってください。

## 環境とログを辿る

OS とカーネル、CPU の命令対応、RAM と swap、空きディスク容量、GPU の VRAM と使用量を確認してください。
利用できる読み取り用の道具には `uname -r`、`lscpu`、`free -h`、`lspci -nnk` があります。
ディスクはモデルを置いているファイルシステムについて調べてください。
WSL やコンテナなら、その種類と GPU の受け渡し、メモリ制限、デバイスへのアクセス権も記録します。
CPU の命令や GPU の計算能力は、実際の報告と起動ログから確認してください。

GPU ごとに、カーネルドライバ、ユーザー側のランタイムと版、SYCL のバックエンド、行列積のバックエンド、実際に選ばれたデバイスを対応付けてください。
Intel の Level Zero、AMD の HIP/rocBLAS、NVIDIA の CUDA/cuBLAS など、利用している構成に絞って調べます。
OS が GPU を認識すること、利用者がデバイスを開けること、SYCL から使えることは別々に確認してください。
GPU の名前だけで対応の有無やエラーの原因を断定せず、対象版の対応条件と読み込まれたライブラリを照合します。

設定やログの既定の場所は次のとおりです。
XDG の環境変数や独自の配置がある場合は、実際の設定と起動方法を優先してください。

| 導入方法 | モデルの設定 | エンジンのログ |
| --- | --- | --- |
| ソース版の setup | XeStrata のフォルダーの `xestrata-<model>.json` | 通常、同じフォルダーの `xestrata-<model>.log` |
| deb/rpm 版 | `$XDG_CONFIG_HOME/xestrata`（既定 `~/.config/xestrata`）の `xestrata-<model>.json` | `$XDG_STATE_HOME/xestrata`（既定 `~/.local/state/xestrata`）の `xestrata-<model>.log` |
| 手動起動 | 起動コマンドで指定された設定 | 設定の `log`、または実際の標準エラーの出力先 |

設定は全体を表示せず、`exe`、`cwd`、`log`、`lib_dirs` と必要なエンジン引数を抽出してください。
モデルの場所も引数と設定から辿ります。
設定の API キーは、設定の有無だけを記録します。
エンジンのログに加えて、setup の失敗ならその実行ログ、server の失敗なら端末のログや traceback を集めてください。
systemd の user service なら、症状の発生時間に絞って `journalctl --user -u xestrata` を調べます。
MCP 経由ならその起動記録も調べてください。
MCP の `strata_logs` が返す setup/server のログは MCP 自身が起動したものなので、ほかの起動方法のログを代替できません。

`xestrata --check` とソース版の `setup.py --check` は、GPU と RAM と CPU の確認に使えますが、setup はその前にデータフォルダーの整理と設定の保存を行います。
`./setup.sh --check` は Python の導入や仮想環境の作成も行うことがあります。
これらも復旧作業の一部として、変更前の情報を残してから使ってください。
ソース版に既存の仮想環境があれば `.venv/bin/python -B setup.py --check` で確認できます。
その結果と終了コードを残し、表示された不足を直した後に同じ条件で確認してください。

## 症状ごとに失敗箇所を絞る

既存の[対処表](DETAILS.ja.md#困ったとき)と対象版のソースを照合し、症状に応じて次を調べてください。
最後に表示されたエラーだけでなく、その原因になった最初のエラーまで戻ります。

| 症状 | 開発者が追えるように残す証拠 |
| --- | --- |
| インストールや依存関係の失敗 | 失敗した操作、対象パッケージと版、終了コード、最初のエラー、利用した配布元。認証付き URL の秘密は除く |
| ビルド失敗 | configure か compile/link か、コンパイラとターゲット、実行コマンド、最初のエラーと前後、失敗したソースと行番号 |
| GPU が使えない | OS での認識、デバイスへのアクセス権、ランタイムの版、SYCL の認識、実際に選ばれた GPU とバックエンド |
| モデル準備や読み込みの失敗 | モデルの取得情報、全分割ファイル、失敗したファイルやテンソル、pack/MTP の状態、最後に成功した読み込みと最初のエラー |
| プロセスが終了する | server と engine のどちらか、終了コードやシグナル、`FATAL signal ... while ...`、SYCL/UR の診断、同時刻のカーネルログ |
| 要求が進まない | 起動、prefill、decode のどこか、最後の進捗、watchdog の報告全文、CPU の各スレッドと GPU/I/O の状態、キューや並列処理の有無 |
| API や画面から使えない | クライアントの種類と版、接続先の構造、要求形式、HTTP ステータス、応答や SSE のエラー、server の状態と traceback |
| 画像や複数 GPU で失敗する | 該当機能の設定と入力、エンコーダーとその停止理由、GPU の選択と層の分割、失敗した段階。文章だけや単一 GPU との比較 |

プロセス終了では、shell の終了値と Python が報告する returncode を区別してください。
SIGKILL だけでは OOM と確定できません。
同時刻のカーネルログの OOM、GPU reset、device lost、PCIe AER など、該当プロセスや GPU を指す記録と照合してください。
メモリ制限のある環境では、その環境の OOM の記録も確認します。
Level Zero の `error: 40` だけでも、VRAM 不足か資源不足かは決まりません。
エンジンが出した段階、空き VRAM、デバイス状態、直前の処理を併せて記録してください。

クラッシュの根拠が不足する場合は、利用可能なクラッシュ記録や対応する実行ファイルからスタックを調べてください。
デバッグシンボルと実行ファイルの一致を確認し、必要なら関係するライブラリの版と Build ID も残します。
取得できたスレッドのスタックと、取得できなかったものを区別してください。
コアダンプ、メモリ、ローカル変数には秘密や会話が含まれ得るため、全文を共有せず、必要な関数名とソース位置を抽出します。
デバッガの attach や計測で実行が変わった場合は、その条件を明記してください。

API の確認は実際のポートと認証方法を使い、接続と要求にタイムアウトを設けてください。
`GET /health` の HTTP 200 は server の応答を示し、モデルが読み込まれた証拠にはなりません。
`loaded`、`GET /v1/status` の `engine_failure` と実行版、`GET /v1/models` を照合し、元の操作に必要な API で短い要求を最後まで実行します。
遅延読み込みでは、要求時にモデルを読み込むので、待機中の `loaded: false` だけで障害と判断しないでください。
認証エラー、接続エラー、キュー待ち、エンジンの失敗、要求形式の問題を区別します。

## 復旧と原因の検証

得られた証拠に合わせて修正し、元の操作を同じ条件で確認してください。
起動できたことに加えて、モデルが読み込まれ、要求がエラーなく完了することを確認します。
設定変更、依存関係の修正、モデルの取得再開、コード修正のどれが成功につながったかを記録してください。
更新や再インストールが効いた場合も、変更前後の版とファイルの違いを追ってください。

モデル、文脈長、GPU、画像、並列数などを変えて動いた場合は、元の条件も直ったか、別の条件で回避できたかを区別してください。
タイムアウトや watchdog を延ばしてエラーが出なくなっただけでは、要求が完了する証拠になりません。
原因の確認が必要でも、OOM、GPU reset、データ破損などを再び起こす試行は避け、保存した証拠を使ってください。
初回の JIT やファイルキャッシュで結果が変わるときは、その条件も記録します。

失敗した版のソースでエラーの出力箇所を探し、呼び出し元、渡された値、失敗に至る条件を追ってください。
関数名、ソースの相対パスと行番号を報告に残し、ライブラリ由来なら XeStrata との呼び出し境界まで示してください。
ソースだけで推測した説明と、実行ログや比較で確認した説明を分けます。
コードを修正したら、変更内容、関係する既存テストと実行結果を残してください。
開発者が修正を取り込むためのビルドと検証の条件は [AGENTS.md](../AGENTS.md#what-goes-in) に従います。

原因を絞れず詰まった場合も、「再インストールを試してください」で終わらせないでください。
同じ試行を繰り返す前に、どの追加情報で候補を区別できるかを決めます。
必要なら、どの関数のどの値や状態を計測すべきか、追加ログの具体的な位置と、その結果で区別できる仮説を示してください。
権限、シンボル、再現入力、ハードウェアなどが不足して進めない場合は、不足しているものと取得方法を報告してください。

## 報告の形式

次の形式で Markdown の報告を作成してください。
根拠は、秘密を除いたエラー原文、ログ抜粋、実行結果、変更内容で示します。
空欄を成功扱いせず、確認できなかった項目と理由を明記してください。
原因が確定していなければ、その不確実さを保ちます。
報告の末尾に、作成したエージェント自身の AI 名（モデル名）と、タイムゾーンを含む ISO 8601 形式の作成日時を記載してください。
モデル名や版を確認できない場合は、推測せず不明と書いてください。

```text
# XeStrata の復旧と原因調査の報告

## 結果

- 復旧した／別条件で回避した／未解決:
- 利用者が期待した操作と実際の症状:
- 最初に動かなかった原因、その根拠、確度:
- 現在できることと残る問題:

## 実行条件

- ソース版／deb／rpm、導入方法:
- Git のコミットと変更の有無、またはパッケージ名と版:
- 起動コマンド、作業ディレクトリ、実行ファイル、バイナリの版:
- 対応するソースの版と、一致を確認した方法:
- ビルドモード、コンパイラ、関係する依存関係の版:
- OS、カーネル、CPU と命令対応、RAM、swap、ディスク、制限:
- GPU、VRAM、ドライバ、ランタイム、選択したデバイスとバックエンド:
- モデルの配布元と版、量子化形式、全分割ファイル、pack/MTP:
- 関係する設定と、秘密を含まない環境変数:

## 再現と証拠

- 発生日時とタイムゾーン、再現頻度:
- 最小再現手順、共有可能な入力、期待する結果と失敗する結果:
- 最後に成功した段階と最初に失敗した処理:
- エラー原文と前後のログ、終了コードやシグナル:
- カーネルやランタイムの診断、取得できたスタック:
- ソース位置と呼び出し関係（対象版との一致を明記）:

## 試したことと変更

| 仮説と確認目的 | 変更前の条件 | 操作や変更 | 結果と証拠 |
| --- | --- | --- | --- |
| | | | |

- 残した変更、その理由、戻す方法:
- 元の操作の成功確認（要求の完了、必要なら画像や複数 GPU）:
- コードを修正した場合の差分、ビルドと既存テストの結果:
- 原因の修正か回避か、他に説明できる原因が残るか:

## 未解決事項と次の確認
```
